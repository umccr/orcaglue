## What This Job Does

This module migrates the legacy [OrcaHouse Glue job](https://github.com/umccr/orcahouse/tree/main/infra/glue/workspace/csv_ica_usage_report).
It is the first stage of processing ICA detailed usage reports and loads the
normalised data into the OrcaVault TSA (Transient Staging Area) layer.

The job:

- Reads every CSV file under the configured `ica-usage-reports/` source prefix.
- Treats the source columns as strings and normalises the known column names.
- Trims whitespace and removes fully empty rows.
- Writes a consolidated CSV, generated SQL schema and JSON audit manifest.
- Uploads the generated artifacts under the Glue-managed `orcaglue/` prefix.
- Loads the validated snapshot into Redshift Serverless through the Data API.

The landing-zone bucket should be organised like this:

```text
orcahouse-dev-landing-zone-.../
├── ica-usage-reports/                 # Raw ICA input CSV files
│   ├── report-1.csv
│   └── report-2.csv
│
└── orcaglue/                          # Glue-managed code and generated artifacts
    └── csv__ica_usage_report/
        └── dev/
            ├── requirements.txt
            ├── csv_ica_usage_report.py
            ├── orcavault_tsa_csv__ica_usage_report.csv
            ├── orcavault_tsa_csv__ica_usage_report.sql
            └── orcavault_tsa_csv__ica_usage_report.manifest.json
```

Raw source reports belong under `ica-usage-reports/` at the bucket root. Do not
put them under `orcaglue/`; that namespace contains the deployed job files and
artifacts generated by the job. S3 creates the source prefix when the first CSV
is uploaded, so an empty folder object is not required and would not count as
input.

The published TSA table is `orcavault.tsa.csv__ica_usage_report`.

### Redshift Safety Tables

The load uses the main target and two safety tables so that a new snapshot can
be checked before it replaces published data.

| Table | Necessity | Purpose |
|---|---|---|
| `csv__ica_usage_report` (main target) | Required | Contains the published snapshot used by downstream consumers. |
| `csv__ica_usage_report__staging` | Strongly recommended | Receives and validates the new snapshot before the main target is modified. |
| `csv__ica_usage_report__previous` | Optional safety feature | Preserves the last published snapshot for manual recovery or comparison. |

Although `__previous` is optional in the general safety design, the current job
expects all three tables because its target-swap SQL always copies the existing
target into `__previous`. Removing it requires a corresponding change to
`build_target_swap_sql()`.

The staging table prevents a failed or incomplete `COPY` from immediately
replacing published data. The previous table provides a recovery point after a
successful swap, but the job does not perform an automatic rollback from it.

### Load and Validation Flow

The job publishes a snapshot as follows:

1. Transform all source CSV files into one normalised CSV and record its row
   count in memory and in the JSON audit manifest.
2. Upload the consolidated CSV, generated SQL and manifest under the
   Glue-managed S3 prefix.
3. In one Redshift Data API batch, delete the old staging rows and `COPY` the
   consolidated CSV into `__staging`.
4. Query the staging row count. If it differs from the transformed CSV row
   count, stop without modifying the main target.
5. In a second batch, replace `__previous` with the current target and replace
   the target with the validated staging snapshot.
6. Query the published target row count and fail the job if it differs from the
   transformed CSV row count.

The batched `DELETE` and `INSERT` statements keep each replacement operation
transactional. The job intentionally avoids Redshift `TRUNCATE` because it
commits immediately and cannot be safely included in the target-swap
transaction.

Validation provides the following protections:

- Unexpected source columns are rejected before loading to detect schema drift.
- The staging count prevents a known incomplete snapshot from replacing the
  target.
- The target count confirms the number of published rows after the swap.
- The manifest records source objects, SHA-256 checksums, row counts and
  duplicate `(usage_id, billing_date)` counts for audit and troubleshooting.

A row-count match validates completeness, not the meaning of every field. If
the final target count fails after the swap has completed, investigate the load
and use `__previous` for a deliberate manual recovery if necessary.

The job does not deduplicate rows. Duplicate `(usage_id, billing_date)` values
are recorded in the manifest for audit only.

## Deployment

We use Pulumi to orchestrate deployment of the ETL.

Authenticate an AWS session with administrator access:

```bash
export AWS_PROFILE=unimelb-warehouse-prod-admin
aws sso login
```

Administrator access is required for `iam:PassRole`. Ask an administrator to
apply the stack changes if you do not have that permission.

Log in to the Pulumi backend:

```bash
pulumi login s3://pulumi-state-115253169271-ap-southeast-2-an/orcaglue
```

> **Important:** _Shared infrastructure prerequisite_
>
> Deploy the updated `shared-infra` stack before deploying this
> job or running it with Redshift loading enabled. This grants the Glue execution
> role the required Redshift Data API permissions: `BatchExecuteStatement` and
> `GetStatementResult`.
>
> From the repository root, preview and apply the existing shared infrastructure
> dev stack:
>
> ```bash
> cd shared-infra
> pulumi stack select dev
> pulumi preview
> pulumi up
> pulumi stack output shared_glue_role_arn
> cd ..
> ```

Review the preview before approving the update. It should include an update to
the Glue role policy. This shared-infrastructure deployment is required once
after the permission changes are introduced; it does not need to be repeated
for every Glue job run.

Change to the module root and initialise the dev stack once, if it does not
already exist:

```bash
cd csv-ica-usage-report
pulumi stack init dev --secrets-provider="awskms://alias/pulumi-state-key"
```

Deploy the ETL:

```bash
pulumi stack select dev
pulumi stack ls
pulumi preview
pulumi up
pulumi stack output
pulumi stack --show-urns
```

A prod stack configuration is intentionally not included because the prod
workspace does not exist for this module yet.

## Local Development

Read [README_LOCAL.md](../README_LOCAL.md) for local development.

Set up the shared Python 3.11 Conda environment as described in
[README_DEV.md](../README_DEV.md).

Authenticate the AWS session and use Granted to export temporary credentials
before creating the Glue container:

```bash
export AWS_PROFILE=unimelb-warehouse-prod-admin
aws sso login
assume unimelb-warehouse-prod-admin
```

Confirm that Granted exported credentials without displaying their values:

```bash
if [[ -n "$AWS_ACCESS_KEY_ID" &&
      -n "$AWS_SECRET_ACCESS_KEY" &&
      -n "$AWS_SESSION_TOKEN" ]]; then
  echo "AWS temporary credentials available"
fi
```

Change to the module root and bring up the local Glue stack:

```bash
cd csv-ica-usage-report
make up
make ps
make glue
```

If the container was created before assuming the role, or the temporary
credentials were refreshed, run `make reload` before `make glue`.

Inside the Glue container, change to the module root and run the diagnostics:

```bash
cd workspace/csv-ica-usage-report/
make debug
```

Run the ETL without loading Redshift:

```bash
make run
```

`make run` reads the source CSV files and uploads the consolidated CSV, SQL and
manifest artifacts, but passes `--load_enabled false` to skip Redshift.

For an isolated test prefix that already contains at least one CSV:

```bash
make run source_prefix=ica-usage-reports-local/your-name/
```

After the artifacts and row counts have been validated, explicitly load the dev
Redshift tables with:

```bash
make run-load
```

Run the focused unit tests from the module root in the Conda environment:

```bash
python -m pytest -q job/test_csv_ica_usage_report.py
```

## Destroy

Destroy only this module's Pulumi resources with:

```bash
pulumi destroy
pulumi stack rm dev
```

Do not destroy or delete the legacy OrcaHouse job until the new TSA table and
downstream OrcaVault dbt chain have been validated and consumers have switched.
